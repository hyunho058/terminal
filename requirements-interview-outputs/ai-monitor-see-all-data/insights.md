# Deep Interview Insights: ai-monitor — 잘린 데이터 전부 보기
> Date: 2026-08-27 ~ 2026-08-28
> Rounds: 8
> Final Ambiguity Score: 0.22 ⚠️ (라운드 1 시점 0.65에서 하락)

## Core Problem

ai-monitor 패널이 섹션 목록을 `+N more`로 잘라 표시하는데, 숨겨진 항목을 읽을 수 있는
수단이 패널에 전혀 없다.

사용자 원문: *"There are more signatures in ai-monitor, but I can't see more except
displayed data. I'd like to see all data using another function."*

인터뷰를 통해 다음으로 확정됐다 — **메모리에 이미 보존된 행 전부를, 고정 크롬은 유지한 채
패널 중앙 리스트 영역의 스크롤로 읽을 수 있게 한다.**

## Key Insights & Decisions

### 인터뷰의 핵심 발견: 하나로 보이던 문제가 실은 둘이었다

- **한계 1 — 렌더링(높이 예산).** 화면의 `+N more`는 패널 높이가 모자라 잘린 것이다.
  섹션별 고정 상한이 아니라 전역 높이 배분기가 라운드로빈으로 한 행씩 나눠주다 멈춘다
  (`crates/renderer/src/monitor_layout.rs:149` `allocate()`, `:828`에서 `+N more` 생성).
  본문은 `.take(rows)`로 앞부분만 그린다 (`:849`). **데이터는 메모리에 전부 살아 있다.**
- **한계 2 — 보존(링버퍼 캡).** 텔레메트리 저장소가 유한 링버퍼다
  (`crates/ai-monitor/src/telemetry.rs:41-75`): `TOOLS_CAP=32`, `FILES_CAP=32`,
  `SUBAGENTS_CAP=32`, `SKILLS_CAP=16`, `TASKS_CAP=64`, `TALLY_CAP=64`.
  밀려난 항목은 메모리에서 영구 소멸하며 디스크 JSONL 재파싱으로만 복구된다.
- **스크린샷의 그 프레임은 한계 1이었다.** 11 / 16 / 7 / 4 는 전부 캡 미만.
- **사용자는 한계 1만 고치기로 선택했다 (D1).** 이 결정 하나가 JSONL 재파싱이라는 큰
  작업 덩어리를 스코프에서 통째로 제거했다. 인터뷰가 만든 가장 큰 절감이다.

### 확정된 결정 (D1–D16)

| # | 결정 | 근거 / 함의 |
|---|------|------------|
| **D1** | **범위 = 메모리 보존분만.** 링버퍼 캡을 넘겨 버려진 이력은 되살리지 않는다 | 순수 렌더링 문제로 확정. JSONL 재파싱 경로 불필요 |
| **D2** | **형태 = 패널 내부 스크롤.** 별도 전체화면도, 파일 덤프도 아니다 | 지배 스펙의 명시적 비목표를 의도적으로 재개 |
| **D3** | **고정 크롬 유지, 리스트 영역만 스크롤.** 헤더·CONNECTED 배지·SESSION 행·스탯 타일·"Last update" 푸터는 제자리 | 스펙 D10의 "fixed chrome / elastic sections" 구조를 보존 |
| **D4** | **여섯 섹션의 모든 행을 전부 펼친다.** TASKS → ACTIVE AGENTS → SKILLS → FILE ACTIVITY → RECENT CALLS → TOOL USAGE 고정 순서 | **`+N more`는 완전히 사라진다.** 현재 높이 배분기의 존재 이유가 소멸 |
| **D5** | **섹션 제목은 스크롤 영역 상단에 고정(sticky)** | 여섯 섹션의 행 모양이 유사해 제목 없이는 현재 위치를 식별 불가 |
| **D6** | **우선 섹션 = RECENT CALLS.** 여섯 중 하나만 고른다면 이것 | 유일하게 확보된 수용 기준 대용물. 검증은 이 섹션 기준으로 설계 |
| **D7** | **휠은 패널이 가져간다** | 패널 위에서 터미널 스크롤백을 굴리던 기존 동작을 **의도적으로 포기** |
| **D8** | **읽던 행에 앵커 고정.** 위쪽에 새 항목이 삽입돼도 읽던 줄은 제자리 | 라이브 갱신 중 위치 유실을 해소. 대신 "위에 새 항목" 신호가 필요해짐 |
| **D9** | **가장자리 통과(edge fall-through).** 스크롤이 양 끝에 닿으면 남는 휠은 터미널 스크롤백으로 | D7이 포기한 동작을 **가장자리에서 부분 복구** |
| **D10** | **휠 대상은 포인터 위치만으로 결정.** 클릭 포커스 없음 | 패널에 포커스 개념 자체가 불필요 — 모달 상태 관리 리스크가 통째로 소멸 |
| **D11** | **숫자 배지로 알림.** 앵커 중 위에 쌓인 항목을 "새 항목 N개"로 표시 | D8의 "조용히 놓침" 문제에 대한 해답 |
| **D12** | **섹션 점프 수단이 필요하다.** TOOL USAGE가 문서 끝에 있는 상태는 수용 불가 | D4가 만든 접근성 회귀를 보정 |
| **D13** | **점프는 키보드 단축키로.** 상시 섹션 인덱스가 아니다 | 인덱스가 세로 공간을 영구히 먹는 것을 회피 |
| **D14** | **자동 상단 복귀 없음.** 사용자가 직접 올리기 전엔 움직이지 않는다 | 읽는 중 화면이 스스로 튀는 일이 절대 없음 |
| **D15** | **앵커 행이 삭제되면 가장 가까운 살아남은 행으로 이동** | 맨 위/맨 아래로 튀지 않음 |
| **D16** | **여섯 섹션 각각에 개별 단축키.** 순환 방식도, RECENT CALLS 단일 키도 아니다. 제시된 예시는 `Cmd+Shift+1` ~ `Cmd+Shift+6` | 한 번에 목표 섹션으로 도달. 터미널에서 여섯 개 조합을 가져온다 |

### 설계를 관통하는 원칙 하나

D8 · D14 · D15는 각각 다른 질문에 대한 답이지만 하나의 원칙으로 수렴한다 —
**화면은 사용자 조작 없이는 절대 스스로 스크롤 위치를 바꾸지 않는다.**
새 항목이 도착해도(D8), 오래 방치돼도(D14), 보던 행이 삭제돼도(D15) 뷰는 튀지 않는다.
구현 시 이 원칙을 불변식으로 삼으면 세 결정이 자동으로 일관된다.

### D4가 뒤집는 것 — 구현 시 반드시 인지할 것

현재 라운드로빈 배분기의 목적은 *"모든 섹션을 한 화면에 압축해 동시에 보여주는 것"*이다.
D4는 그 보장을 "전부 도달 가능"으로 교체한다. 따라서 이 작업은 `allocate()`에 스크롤을
얹는 것이 아니라 **그 함수의 역할을 재정의하는 것**이다. 3단계 라운드로빈
(`monitor_layout.rs:179-192`)과 `+N more`(`:828`)는 D4 하에서 죽은 코드가 된다.

## Defined Requirements

- 메모리에 보존된 모든 행이 패널 안에서 읽을 수 있어야 한다 (D1, D2).
- 고정 크롬 요소는 스크롤과 무관하게 항상 제자리에 있어야 한다 (D3).
- 스크롤 영역은 여섯 섹션 전체를 고정 순서로 완전히 펼쳐 담는다 (D4).
- 섹션 제목은 해당 섹션을 읽는 동안 상단에 고정되어야 한다 (D5).
- `+N more` 표기는 제거된다 (D4의 귀결).
- 패널 영역 위의 휠 입력은 포인터 위치만으로 패널 스크롤을 구동한다 (D7, D10).
- 스크롤이 양 끝에 닿으면 남는 휠 입력은 터미널 스크롤백으로 전달된다 (D9).
- 스크롤된 상태에서 새 항목이 도착해도 읽던 행의 화면 위치는 유지된다 (D8).
- 앵커 중 위쪽에 도착한 항목의 개수를 숫자 배지로 표시한다 (D11).
- 뷰는 사용자 조작 없이는 절대 스스로 스크롤 위치를 바꾸지 않는다 (D8, D14, D15).
- 앵커 행이 삭제되면 가장 가까운 살아남은 행으로 이동한다 (D15).
- 여섯 섹션 각각으로 직접 이동하는 개별 키보드 단축키를 제공한다 (D12, D13, D16).
- **완료 판정 대용 기준:** RECENT CALLS의 메모리 보존분(최대 32개) 전체가 스크롤로
  도달 가능해야 한다 (D6).

## Identified Risks & Failure Modes

- **셰이핑 캐시 오염 (최우선 기술 리스크).** 캐시 키는
  `(model, panel_rect, scale, cell)` + 아틀라스 `(epoch, generation)`
  (`crates/renderer/src/monitor_panel.rs:201-225, 432-440`). **스크롤 오프셋이 키에 없으므로
  렌더러 측 오프셋만 바꾸면 낡은 캐시에 조용히 적중해 화면이 갱신되지 않는다.**
  오프셋·sticky 헤딩·배지 카운트 상태는 반드시 키(또는 모델)에 편입돼야 한다.
- **패널 성능 예산.** 패널은 PTY 출력·커서 이동·포커스 변경·드래그 중 매 `CursorMoved`마다
  다시 그려진다 (`monitor_panel.rs:181-197`). 캐시 미스 시 `MonitorModel` 전체를 클론한다
  (`:442-453`). D4로 문서가 길어지면 전체 레이아웃 비용이 커지므로, 스크롤이 매 프레임
  캐시를 깨면 과거에 폐기한 "매 프레임 재레이아웃" 부채가 되살아난다.
- **휠 소유권 회귀 (D7, 명시적으로 수용됨).** 패널 위에서 터미널 스크롤백을 굴리던 동작이
  사라진다. D9가 가장자리에서만 부분 복구한다. 추가가 아니라 **교환**이다.
- **단축키 여섯 개를 터미널에서 가져옴 (D16).** 패널이 열려 있는 동안 zsh가 해당 조합을
  받지 못한다. 현재 패널이 먹는 키는 `Cmd+Shift+M` 하나뿐이므로 입력 채널 점유가
  7배로 늘어난다.
- **배지 방치 (D14의 대가).** 자동 복귀가 없으므로 사용자가 스크롤한 채 잊으면 배지 숫자만
  쌓이고 라이브 활동을 계속 놓친다. D11의 배지가 유일한 방어선이다.
- **긴 문서에서의 탐색 저하 (D4의 대가).** 전부 펼치면 원하는 행을 찾기가 오히려 느려질 수
  있다. D16의 섹션 점프가 유일한 완화책이다.
- **위젯 크레이트 유혹.** 스크롤 뷰포트·sticky 헤딩은 GUI 툴킷이 주는 것들이다.
  `.claude/rules/no-gui-crates.md`가 금지한다 — 전부 셀 위에 손으로 그려야 한다.
- **성공 기준 부재.** 무엇이 되면 됐는지가 D6 외에는 정의되지 않아, 만든 뒤
  "이게 맞나"를 판정할 근거가 약하다.

## Open Questions & Unknowns

- **빈도 — 사용자가 "모르겠다"로 답함.** `+N more` 때문에 답답했던 상황이 하루 몇 번인지,
  세션당 몇 번인지, 장애 대응 때만인지 알 수 없다. 세 차례 물었고 억지로 정하지 않았다.
- **구체적 실패 장면.** `+N more`를 보고 포기했던 실제 순간이 끝내 제시되지 않았다.
  D6(RECENT CALLS 지목)이 그 대용물 역할을 하고 있다.
- **회귀 신호(anti-success).** 일주일 후 "실수였다"고 느끼게 할 행동이 무엇인지 미답변
  (선택 질문이었음). 위 Risks의 세 가지 대가 — 휠 회귀, 긴 문서 탐색 저하, 배지 방치 —
  가 후보다.
- **단축키 조합의 최종 확정.** D16은 개별 키 방식을 택했고 예시로 `Cmd+Shift+1`~`6`이
  제시됐으나, 사용자가 그 문자열을 직접 타이핑해 확인한 것은 아니다. 스펙 작성 시
  재확인이 필요하다.
- **창 높이를 키우는 기존 회피책**을 시도해 봤는지, 왜 불충분했는지.
