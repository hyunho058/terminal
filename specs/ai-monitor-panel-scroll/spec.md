## Goal
ai-monitor 패널이 섹션 목록을 `+N more`로 잘라 표시하는데, 숨겨진 항목을 읽을 수 있는
수단이 패널에 전혀 없다. 메모리에 이미 보존된 행 전부를, 고정 크롬은 유지한 채 패널
중앙 리스트 영역의 스크롤로 읽을 수 있게 한다.

원문: *"There are more signatures in ai-monitor, but I can't see more except displayed
data. I'd like to see all data using another function."*

## Non-goals
- 링버퍼 캡(`TOOLS_CAP=32` 등)을 넘겨 메모리에서 사라진 이력의 복원 — JSONL 재파싱 경로 없음 (D1)
- 별도 전체화면 뷰 / 파일 덤프 등 패널 외부의 표시 수단 (D2)
- 텔레메트리 링버퍼 캡 증설
- 패널에 클릭 포커스 개념 도입 (D10)
- 상시 표시되는 섹션 인덱스 UI (D13)
- GUI/위젯 크레이트 도입 — 스크롤 뷰포트와 sticky 헤딩은 셀 위에 손으로 그린다 (`.claude/rules/no-gui-crates.md`)

## Confirmed Goal
ai-monitor 패널의 리스트 영역을 스크롤 가능한 뷰포트로 재정의한다. 여섯 섹션(TASKS →
ACTIVE AGENTS → SKILLS → FILE ACTIVITY → RECENT CALLS → TOOL USAGE)을 고정 순서로
**완전히 펼쳐** 하나의 긴 문서로 만들고, 헤더·CONNECTED 배지·SESSION 행·스탯 타일·
푸터 줄(평소 "Last update", 새 항목이 있으면 배지 — D34)은 고정 크롬으로 제자리에
남는다. `+N more`와 라운드로빈 높이 배분은
사라진다 — 스크롤을 얹는 것이 아니라 `allocate()`의 역할을 재정의하는 작업이다.

**포함:** 리스트 영역 스크롤 뷰포트 · sticky 섹션 제목 · 포인터 위치로 결정되는 휠 소유권
+ 가장자리 통과 · 읽던 행 앵커 고정 · "새 항목 N개" 배지 · 여섯 섹션 개별 점프 단축키.

**완료 판정:** RECENT CALLS의 메모리 보존분(최대 32개) 전체가 패널 스크롤만으로 도달
가능하고, 스크롤 중 라이브 갱신이 들어와도 읽던 행이 제자리를 지키며, 고정 크롬이 한 번도
흐르지 않는다.

**미정으로 남는 것 (인터뷰가 닫지 못함):**
- 빈도 데이터 없음 — 사용자가 "모르겠다"로 답함
- 성공 기준은 D6(RECENT CALLS) 하나뿐
- 단축키 조합 `Cmd+Shift+1`~`6`은 예시일 뿐 사용자 확정 아님 → L2에서 재확인
  (→ L2에서 확정됐으나 실제 사용에서 macOS 스크린샷 예약과 충돌해 `Cmd+Opt`로 개정. D16 참조)

## Research

### 지워질 코드 — D4가 역할을 재정의하는 지점
- `allocate()`는 3단계(헤딩 예약 → 섹션당 1행 → 라운드로빈)로 높이를 배분한다
  (`crates/renderer/src/monitor_layout.rs:149-194`). **유일한 호출자는 `Painter::sections`**
  (`:782-806`) — D4 하에서 이 함수 전체가 죽는다. `Grant { heading, rows }`(`:122-129`)도 함께.
- `body()`가 `.take(rows)`로 앞부분만 그린다 (`:849-872`, Cards/Rows/Bars 세 갈래 전부).
- `+N more`는 heading에 실려 그려진다 (`:814-847`, 생성은 `:823-831`).

### ⚠️ `+N more`는 두 가지를 동시에 세고 있다 — 인터뷰가 놓친 사실
`hidden = section.total.saturating_sub(shown.min(section.body.len()))` (`monitor_layout.rs:823`).
`Section::total`은 **세션 누적 총계**이고 `body.len()`은 **링버퍼에 남은 것**이다
(`monitor_model.rs:284-288`이 명시: "The session total, which may exceed `body.len()`").
따라서 `+N more`는 ①높이 부족으로 잘린 행 + ②링버퍼에서 밀려난 행을 **합쳐서** 보고한다.
D4가 ①을 0으로 만들어도 **②는 남는다** — 예: TOOL USAGE는 앱이 `TOOL_BARS = 9`로 캡하지만
tally는 최대 64개 이름을 갖는다 (`dashboard.rs:830-836`, 테스트에서 `total == 11`,
`dashboard.rs:2371`). 전부 펼쳐도 `+2 more`가 남는다. **"`+N more`는 완전히 사라진다"(D4)를
그대로 구현하면 링버퍼 손실이 조용히 은폐된다.** → L2 결정 필요.

### 셰이핑 캐시 — 함정과 그 함정의 이미 존재하는 해법
- 캐시 키는 `Shaped { model, panel, scale, cell }` (`monitor_panel.rs:201-207`), staleness 판정은
  `monitor_panel.rs:432-440`, 아틀라스 식별자 `(epoch, generation)`는 `:479-488`.
- **`MonitorModel`이 `PartialEq`를 derive한다** (`monitor_model.rs:307`). 즉 **스크롤 상태를
  `MonitorModel`에 넣으면 캐시 무효화가 공짜로 따라온다** — 별도 키 필드를 추가하는 것보다
  안전하다(키 추가는 "넣는 걸 잊으면 조용히 안 됨"이 남지만, 모델 필드는 `!=`가 자동으로 잡는다).
- 그 패턴의 선례가 이미 있다: 사이드바는 `SidebarHandle::set_list_scroll(list_top, scroll_px)`로
  스크롤을 렌더러 모델에 밀어 넣는다 (`sidebar_row.rs:632-636`, 호출부
  `terminal_app.rs:1267-1275`). `MonitorHandle`은 현재 `set()` 하나뿐 (`monitor_panel.rs:55-61`).
- 캐시 미스 비용: `MonitorModel` 전체 클론 (`monitor_panel.rs:442-453`). D4로 문서가 길어지면
  `layout()` 비용도 함께 커진다.

### 휠 라우팅 — 확장 지점과 완성된 선례
- **단 하나의 순서 있는 hit-test**가 라우팅을 소유한다 (`terminal_app.rs:2594-2618`):
  `sidebar_layout::hit_test` → 사이드바, `None` → `wheel_grid`. 패널은 현재 `None`으로 떨어져
  터미널 스크롤백을 굴린다 — D7이 포기하겠다는 바로 그 동작.
- 순수 함수 선례가 전부 갖춰져 있다: `wheel_scroll` (`input.rs:587-603`),
  `content_height` / `max_scroll` / `clamp_scroll` (`sidebar_layout.rs:352-368`),
  그리고 **`scroll_to_reveal(index, s, inp)`** (`sidebar_layout.rs:372-`) — D16 섹션 점프의 원형.
- 서브라인 잔여분 누적기 `wheel_lines(delta, cell_h, &mut wheel_accum)` (`input.rs:610-`) —
  트랙패드가 동작하는 이유. **D9의 가장자리 통과는 이 누적기를 패널과 그리드가 어떻게
  나눠 쓰는지를 결정해야 한다** (인터뷰가 다루지 않음).
- `wheel_grid`는 마우스 프로토콜 앱에 휠을 먼저 넘긴다 (`terminal_app.rs:1899-1909`).
  D9의 통과분은 이 함수를 거쳐야 그 계약이 유지된다.
- 리드로우 구분: 사이드바 전용 변경은 `window.request_redraw()` (`:2613`), 콘텐츠 변경은
  `redraw()`가 `snapshot_dirty`를 세운다 (`:1869-1872`). 패널 전용 변경은 전자.
- 패널 밴드 좌표는 이미 순수 함수로 있다: `input::monitor_edge_x(viewport_w, right_inset)`
  (`input.rs:398`), `in_monitor_grab_band` (`:413`, 드래그 전용).

### ⚠️ D16은 기존 결정을 명시적으로 뒤집는다
`Overlay::on_key`는 토글 외 **어떤 키도 잡지 않겠다고 문서화되어 있다**
(`overlay.rs:1568-1571`): *"A monitor doesn't capture other keys (D1/R1.2/R1.3): no `Esc`,
no `q`. The panel never takes focus."* D16의 여섯 단축키는 이 결정의 번복이다 — 스펙이
그렇게 기록해야 한다. `Cmd+Shift+*` 계열은 이미 M(모니터)/R(리네임)/사이드바 토글이
점유 중 (`input.rs:215-222`).

### 앵커·배지가 필요로 하는 것 (D8/D11/D15)
- `Card`/`Row`/`Bar`에 **안정적 식별자가 없다** (`monitor_model.rs:183-236`) — 전부 표시용
  문자열. "읽던 행"을 프레임 간에 다시 찾으려면 식별 수단이 필요하다. TASKS만 크레이트 쪽에
  id를 갖는다 (`dashboard.rs:603`의 `(String, TaskEntry)`), 나머지 다섯은 없다.
- 스냅샷은 **누적(cumulative)**이며 최신 것만 남기고 합쳐진다 (`overlay.rs:1521-1535`
  `drain_to_newest`). 즉 "무엇이 새로 추가됐는가"는 모델 diff로 도출해야 한다.

## Decisions

> D1–D16은 `requirements-interview-outputs/ai-monitor-see-all-data/insights.md`가 닫은
> 사용자 결정이다. 번호를 유지해 추적성을 보존하고, 이 스펙이 새로 여는 결정은 D17부터 붙인다.

### D1: 범위 = 메모리 보존분만
- **Status**: resolved (interview)
- **Rationale**: 링버퍼 캡을 넘겨 버려진 이력은 되살리지 않는다. 순수 렌더링 문제로 확정되며,
  JSONL 재파싱 경로가 통째로 스코프에서 빠진다. 기각된 대안: 디스크 재파싱(작업량이 본
  기능의 몇 배이고, 화면이 안 보이는 문제와 데이터가 없는 문제는 다른 문제다).

### D2: 형태 = 패널 내부 스크롤
- **Status**: resolved (interview)
- **Rationale**: 별도 전체화면 뷰도, 파일 덤프도 아니다. 지배 스펙(`specs/ai-monitor`)의
  명시적 비목표를 의도적으로 재개하는 결정이다.

### D3: 고정 크롬 유지, 리스트 영역만 스크롤
- **Status**: resolved (interview)
- **Rationale**: 헤더·CONNECTED 배지·SESSION 행·스탯 타일·푸터 줄은 제자리. (푸터 줄의
  *내용*은 D34에 따라 "Last update"와 배지 사이를 오가지만, 그 **자리**는 고정이다.)
  스펙 D10의 "fixed chrome / elastic sections" 구조를 보존한다. 코드상 이미 `footer_top`이
  모든 영역의 천장으로 먼저 해결된다 (`monitor_layout.rs:230`).

### D4: 여섯 섹션의 모든 행을 전부 펼친다
- **Status**: resolved (interview)
- **Rationale**: TASKS → ACTIVE AGENTS → SKILLS → FILE ACTIVITY → RECENT CALLS → TOOL USAGE
  고정 순서. **`allocate()`의 존재 이유가 소멸한다** — 스크롤을 얹는 게 아니라 그 함수의
  역할을 재정의하는 작업이다. 기각된 대안: 섹션별 상한을 늘리기(잘림의 위치만 옮길 뿐 문제가
  남는다), 라운드로빈 유지 + 섹션별 개별 스크롤(여섯 개의 스크롤 상태와 여섯 개의 휠 대상).
- **⚠️ 명시적으로 수용하는 대가 — 보장의 종류가 바뀐다.** 현재 라운드로빈의 계약은
  *"상호작용 0으로 여섯 섹션이 동시에 보인다"*이고, 그 성질이 패널을 **주변시(ambient)
  모니터**로 만든다. D4는 그것을 *"상호작용을 하면 전부 도달 가능하다"*로 교체한다.
  사용자의 원문 불만은 **도달성**이었지 동시 가시성이 과하다는 것이 아니었으므로, D4는
  요청된 것을 주면서 **요청되지 않은 것을 대가로 가져간다**. 그 교환의 정당성을 판정할
  유일한 축(깊게 읽는 경우 대 흘긋 보는 경우의 빈도 비율)은 사용자가 명시적으로
  "모르겠다"고 답해 **존재하지 않는다**. 검토했으나 기각한 중간안 — *문서가 뷰포트에
  들어가면 오늘처럼 압축, 넘치면 스크롤* — 은 레이아웃이 세션 길이에 따라 **모양을 바꾸고**
  죽은 줄 알았던 라운드로빈이 살아남는다는 이유로 버렸다. **이 대가는 D25와 결합해
  더 커진다 — D25를 볼 것.**
- **⚠️ 개정 2026-08-31 — 위에서 "수용한 대가"가 실제로 청구됐다.** 구현이 끝난 뒤 사용자가
  이렇게 말했다: *"나는 그리고 5개가 넘어가면 접었다 폈다하는 기능을 원했던건데."* 즉 위
  경고가 정확히 짚은 그 성질 — 상호작용 0으로 여섯 섹션이 동시에 보이는 것 — 이 실제로
  필요한 것이었고, 그 판정을 내릴 유일한 축이 "모르겠다"로 비어 있었기 때문에 스펙 단계에서
  결론이 나지 않았던 것이다. **D4는 철회되지 않는다** — 문서는 여전히 모든 항목을 담고,
  `+N more`는 여전히 없다. 대신 D39~D42가 그 문서 위에 **접기**를 얹어, 위에서 기각했던
  중간안("들어가면 압축, 넘치면 스크롤")이 왜 옳지 않았는지는 유지하면서(레이아웃이 세션
  길이에 따라 저절로 모양을 바꾸는 일은 여전히 없다) 압축 여부를 **사용자가 정하게** 한다.
  기각안과의 차이가 이 개정의 핵심이다: 기각된 것은 **자동** 압축이었고, 채택된 것은
  **사용자가 조작하는** 압축이다.

### D5: 섹션 제목은 스크롤 영역 상단에 고정(sticky)
- **Status**: resolved (interview)
- **Rationale**: 여섯 섹션의 행 모양이 유사해 제목 없이는 현재 위치를 식별할 수 없다.

### D6: 우선 섹션 = RECENT CALLS
- **Status**: resolved (interview)
- **Rationale**: 여섯 중 하나만 고른다면 이것. 인터뷰가 확보한 유일한 수용 기준 대용물이며,
  검증은 이 섹션을 기준으로 설계한다.

### D7: 휠은 패널이 가져간다
- **Status**: resolved (interview)

### D18: sticky 제목은 **밀어내기(push-off)** 의미를 갖되, D17 아래에서 경계 교체로 실현된다

### D20: 링버퍼 손실은 **별도 문구로 밝힌다**
- **Status**: resolved
- **Rationale**: `+N more`는 ①높이 부족으로 잘린 행과 ②링버퍼에서 밀려난 행을 합쳐 세고
  있었다 (`monitor_layout.rs:823`: `total.saturating_sub(shown.min(body.len()))`;
  `monitor_model.rs:284-288`이 `total > body.len()`을 명시). D4는 ①만 0으로 만든다.
  `+N more`는 D4대로 사라지되, `total > body.len()`인 섹션은 **메모리에 없는 것이 있다**는
  사실을 다른 문구로 말한다 (예: `32 of 400`).
  기각된 대안 ①**완전 제거**: "이제 전부 보인다"가 거짓이 되고, 사용자가 목록 길이와 총계
  숫자를 대조해 스스로 추론해야 한다 — 이 기능이 없애려던 바로 그 부담이다.
  ②**`+N more` 유지 + 의미 재정의**: 같은 문구가 다른 뜻을 갖게 되어, 스크롤하면 나올
  것처럼 오해를 계속 생산한다.
- **경계:** 이 문구는 D1을 뒤집지 않는다 — 손실을 **복구**하지 않고 **고지**만 한다.
- **문구는 기존 `total` 마크를 대체한다, 병기하지 않는다.** 헤딩은 이미 `section.total`을
  `mark_right`로 그린다 (`monitor_layout.rs:822`). 손실 문구를 **추가**하면 총계가 두 번
  나오고 가로 공간을 두 배로 먹는다. `total > body.len()`인 섹션에서는 그 마크가
  `32 of 400` 형태로 **바뀌고**, `total == body.len()`이면 오늘과 같은 총계 하나다.
- **좁은 패널 폴백 — `mark_right`는 안 들어가면 통째로 버린다** (`:432`: *"draw nothing
  at all if it does not fit whole"*, 잘린 마크가 거짓을 말하기 때문). 손실 문구가 폭에
  안 맞으면 **총계 단독 마크로 되돌아간다** — 두 마크 다 못 넣는 폭에서는 오늘과 동일하게
  아무것도 안 그린다. 반쪽 진실은 어느 경우에도 그리지 않는다.

### D31: 콘텐츠 뷰포트는 sticky 슬롯 **아래**에서 시작하고, 슬롯을 침범하는 항목은 컬링된다

- **Rationale**: 그래서 겹침 자체를 만들지 않는다. 스크롤 콘텐츠의 뷰포트 상단을 sticky
  슬롯의 **아래 모서리**로 정의하면, 어떤 항목도 슬롯 영역에 그려지지 않으므로 가릴 필요가
  없다. 슬롯에는 현재 섹션의 헤딩 사본 하나만 그린다.
  기각된 대안 ①**시저 렉트**: C1 위반이며 GPU 경로를 확장한다. ②**패스 순서 재배치 /

  놓이는 첫 항목**이다. D22의 "마지막 섹션 헤딩이 상단에 오는 인덱스"도 이 기준으로 읽는다
  — 그 헤딩이 슬롯에 복제되는 위치를 뜻한다.
- **⚠️ 항목 `i`가 헤딩이면 슬롯이 그것을 **소비**하고 콘텐츠는 `i+1`부터 그린다.** D32에
  의해 헤딩도 항목이므로, 이 규칙이 없으면 같은 헤딩이 슬롯과 그 바로 아래에 **연속 두
  줄**로 나온다. 그리고 그 상태는 예외가 아니라 **기본값**이다 — 인덱스 0(D25가
  개방·탭전환마다 강제), D16의 여섯 점프 착지점 **전부**, D22의 `max_index`가 모두 헤딩
  인덱스다.

    인덱스**를 가리킨다(`i+1`이 아니다). `i+1`은 그 인덱스에서 콘텐츠가 시작하는 지점일
    뿐, 스크롤 상태로 저장되는 값이 아니다.
  - **⚠️ `h+1`은 유효한 정지점이 아니다 — 사다리에서 건너뛴다.** 헤딩 인덱스 `h`에서는
    슬롯이 `h`를 소비하고 콘텐츠가 `h+1`부터 그려지는데, 인덱스 `h+1`에서도 슬롯이
    (오프스크린) 헤딩 `h`의 사본을 그리고 콘텐츠가 역시 `h+1`부터다 — **두 상태의 프레임이
    완전히 동일하다.** 그대로 두면 섹션 경계마다 굴렸는데 아무것도 안 변하는 "죽은 휠
    클릭"이 하나씩, 여섯 섹션이면 여섯 번 생긴다. `h`에서 아래로 굴리면 `h+2`로, `h+2`에서
    위로 굴리면 `h`로 간다.
- **섹션 영역이 슬롯 한 줄보다 낮을 때: 슬롯만 그리고 콘텐츠는 그리지 않는다.** R5.1
  스윕이 2px부터 돌므로 그 구간은 반드시 존재하며, 오늘은 `allocate`가 그 구간을
  정의했으나 D4가 그 함수를 죽인다. 슬롯조차 못 들어가면 섹션 영역 전체를 그리지 않는다 —
  고정 크롬은 D3/C2대로 남는다.
- **대가(수용):** 뷰포트가 헤딩 한 줄만큼 영구히 줄어든다.

  - **anchored** (상단 인덱스 > 0): D8·D11·D15·D19가 그대로 적용된다.
  0에서 벗어나면 무장(앵커 = 그때의 상단 항목), 0으로 돌아오면 해제. 이것이 D33의
  근거(*"상단에 도달하면 위에 안 본 것이 없다"*)를 정합적으로 만드는 유일한 해석이다.
- **⚠️ 모드는 상단 인덱스의 순수 함수다 — 별도 래치가 아니다.** "전이는 사용자 조작으로만"은
  *인덱스가 바뀌는 방식*을 말하는 것이지 모드 판정을 말하는 것이 아니다. 둘을 구분하지
  않으면 **문서가 줄어들 때 모순이 생긴다**: anchored 상태에서 앵커 위 항목들이 사라지면
  (D15가 다루는 바로 그 상황) 상단 인덱스가 사용자 조작 없이 0까지 내려올 수 있다.
  그때는 **following이다** — 인덱스가 0이므로. 파생 정의라야 D33("인덱스 0에서 배지 0")과
  어긋나지 않는다.
- **C7을 이에 맞춰 읽는다:** C7이 지키는 것은 "화면 내용이 안 바뀐다"가 아니라
  **"사용자가 읽던 위치를 잃지 않는다"** 이다. following 상태에는 지킬 위치가 없으므로
  새 항목이 나타나는 것은 C7 위반이 아니다.
- 기각된 대안 **개방 시에도 즉시 anchored**: 규칙이 하나로 줄지만 패널이 모니터이기를
  그만둔다 — 사용자가 아무것도 안 했는데 화면이 굳는다.

  레이아웃 상태와 나란히 두는 것과 같은 모양이다 (`sidebar_row.rs:632-636`).
- **이 스펙의 최우선 함정:** 인터뷰가 1순위 기술 리스크로 지목한 "오프셋이 캐시 키에
  없어 낡은 캐시에 조용히 적중"은 **2단 키에서 여전히 살아 있다**. 1단에서 빼는 것과
  2단에 넣는 것은 반드시 함께 이뤄져야 한다.

### D29: 배지는 **고정 크롬에 상주**한다 — 스크롤 위치와 무관하게 항상 보인다
- **Status**: resolved (Inversion Probe에서 도출)
- **Rationale**: Inversion이 "배지 방치"를 최우선 실패 시나리오로 지목했고, D11의 배지가
  유일한 방어선이다. **방어선이 스크롤 영역 안에 있으면 스크롤한 사용자에게 안 보인다** —
  방어선이 필요한 정확히 그 상황에서 사라진다. D3이 고정 크롬은 스크롤과 무관하게 항상
  제자리라고 보장하므로, 거기 두면 그 실패가 구조적으로 불가능해진다.
  기각된 대안 ①**스크롤 영역 상단의 떠 있는 알약**: 방향성이 직관적이지만 sticky 제목과
  가로 공간을 다투고, 패널이 좁을 때 둘 중 하나가 잘린다. ②**섹션 제목마다 신규 수**:
  정보량은 가장 많지만 **방치 문제를 못 막는다** — 아래로 굴리면 위쪽 섹션의 제목이
  화면 밖이라 그 배지가 안 보인다.
- **대가(수용):** 어느 섹션에 새 것이 왔는지는 알려주지 않는다. 총합 하나다.
- **"구조적으로 불가능"은 영역을 지정해야 참이 된다** — 고정 크롬도 짧은 패널에서는
  역순으로 항복하기 때문이다. 어느 영역인지는 **D34**가, 언제 0이 되는지는 **D33**이 정한다.

### D30: 맨 위 복귀 = **`Cmd+Opt+1`** — 새 상호작용을 만들지 않는다
- **Status**: resolved (Inversion Probe에서 도출)
- **Rationale**: TASKS가 문서의 첫 섹션이므로 D16의 첫 키가 이미 맨 위 복귀다. D14가

  기각된 대안 ①**배지 클릭**: 가장 직접적이지만 패널에 첫 클릭 타겟이 생기고 히트테스트·
  호버 상태가 따라온다 — D10이 없앤 상태 관리 리스크를 다른 문으로 들인다.
  ②**전용 키(`Cmd+Shift+↑` 등)**: 의미는 명확하나 zsh에서 가져오는 조합이 여섯에서
  일곱으로 늘고 `Cmd+Opt+1`과 기능이 겹친다.
- **⚠️ 이 결정이 성립하려면 배지가 그 키를 함께 말해야 한다.** 배지를 본 사람이
  "`Cmd+Opt+1`을 누르면 된다"를 알아낼 경로가 없으면 D30은 복귀 수단이 아니라
  복귀 수단의 **부재**다. → L3 요구사항으로 내린다.
  **한정:** 카운트와 키 힌트가 함께 들어가는 폭(기본 430px / 16px 셀 포함)에서 충족된다.
  사용자가 드래그로 좁힌 패널에서는 D34의 잘림 순서에 따라 힌트가 먼저 사라지며, 그
  성능 저하는 **수용된 대가**다 — 카운트(경보)가 힌트(편의)보다 우선하기 때문이다.
- **⚠️ 이것이 이 스펙의 두 번째 설계 번복이다** (첫째는 D16의 `overlay.rs:1568-1571`).
  푸터는 키캡을 그리지 않기로 명시적으로 결정돼 있다 (`monitor_layout.rs:756-759`):
  *"The design's `q` keycap is deliberately absent (D1/R1.4): the panel consumes no
  keystroke but the chord, so drawing a keycap would promise a binding that does not
  exist and would cost a terminal user their `less` quit key if it did."* 배지가 키를
  광고하는 것은 정확히 그 키캡을 되살린다. **번복의 근거는 그 결정의 전제가 바뀌었다는
  것이다** — 이제 패널은 실제로 그 바인딩을 갖고(D16), 그것은 `less`의 `q` 같은 단일
  문자가 아니라 수식자 조합이며, 패널이 열려 있을 때만 유효하다. 즉 원래 결정이 막으려던
  두 해악(없는 약속 / 터미널 키 강탈)이 **둘 다 해당하지 않는다**. 그리고 배지는 D34에
  의해 푸터에 산다 — 같은 줄이다.

### D39: 항목이 **5개를 넘는** 섹션은 접힌다 — 문턱은 `FOLD_THRESHOLD = 5`
- **Status**: resolved (구현 후 사용자 요청, 2026-08-31)
- **Rationale**: D4가 대가로 내준 "흘긋 보면 여섯 섹션이 다 보인다"를 되찾되, D4가 산 것
  (모든 항목이 문서에 존재한다)은 잃지 않는 방법. 접힌 섹션은 앞의 5개와 컨트롤 한 줄을
  그리고, 나머지는 **문서에서 사라지는 게 아니라 사다리에서 빠진다** — 펴면 그대로 돌아온다.
  **정확히 5개인 섹션은 접히지 않는다**(`>`, `>=`가 아니다): 아무것도 숨기지 않는 컨트롤은
  rung 하나를 쓰면서 아무도 안 한 질문에 답한다.
- **기본값은 접힘.** RECENT CALLS 하나가 수십 줄까지 가고, 나머지 다섯 섹션을 보려고 그걸
  전부 지나쳐야 하는 상태가 애초의 불만과 같은 모양이다. 펴는 비용은 클릭 한 번이다.
- **⚠️ 이것은 `+N more`의 부활이 아니다.** 그 마크는 높이 배분기가 **이미 버린** 행을 사후
  보고했고 거기에 도달할 수단이 없었다 — 그 도달 불가능성이 이 기능 전체의 출발점이다.
  접기는 문서가 **여전히 들고 있는** 행을 감추며, 컨트롤 자체가 도달 경로다. 두 개가 같은
  단어("more")를 쓰기 때문에 R9.1을 지키던 테스트가 단어만 보고 있었고, 그대로 두면 자기가
  막으려던 문제의 **해결책**에 대고 발동한다. 옛 마크의 형태(`+`로 시작)를 보도록 좁혔다.

### D40: 컨트롤 rung은 **두 상태 모두에** 존재한다
- **Status**: resolved
- **Rationale**: 접혔을 때 `▸ N more`, 폈을 때 `▾ collapse`. 펴는 순간 사라지는 컨트롤은
  되돌아갈 길을 없앤다. 문구는 `folded()` 하나에서 파생되므로 두 상태가 어긋날 수 없다.
- `ItemKind::Fold`는 사다리의 정식 rung이다 — 스크롤로 도달하고, 정지점이 되고, 클릭된다.
  `entry: None`이라는 점에서 제목과 같은 부류이며, 그래서 `Item::is_body()`가 추가됐다:
  "본문 항목"을 세던 기존 테스트들이 `!is_heading()`으로 그 뜻을 대신하고 있었는데, 그
  대체는 rung 종류가 셋이 되는 순간 무너진다.

### D41: 클릭 대상은 **제목 줄과 컨트롤 줄** 둘뿐이다 — D10을 되돌린다
- **Status**: resolved
- **Rationale**: 행은 클릭해도 아무 일도 없다. 초당 몇 번씩 갱신되는 목록에서 아무 행이나
  클릭이 문서를 바꾸면, 사용자가 의도하지 않은 접힘이 상시로 일어난다. **고정 슬롯의 제목도
  클릭 대상이다**: 섹션 안으로 스크롤해 들어가면 그 제목은 슬롯에만 남으므로, 슬롯이 답하지
  않으면 지금 읽고 있는 섹션만 접을 수 없게 된다.
- **⚠️ 이것이 이 스펙의 세 번째 설계 번복이다** (D16의 키 점유, D30의 푸터 키캡에 이어).
  D10은 *"휠 대상은 포인터 위치만으로 결정. 클릭 포커스 없음 — 패널에 포커스 개념 자체가
  불필요, 모달 상태 관리 리스크가 통째로 소멸"* 이었다. 클릭 타겟은 그 리스크를 다시 들인다.
  **번복의 범위를 좁힌 형태**: 여전히 포커스도, 호버 상태도, 모달도 없다. 들어온 것은 좌표
  하나를 rung 하나로 바꾸는 순수 함수(`monitor_scroll::hit`)뿐이고, 앱은 여전히 기하 계산을
  하지 않는다 — 패널이 자기가 발행한 밴드에 좌표를 맞춰 보고 섹션 번호만 돌려준다. 휠이
  이미 쓰던 분업 그대로다.
- **밴드 밖으로 잘린 rung은 클릭되지 않는다.** C1(scissor rect 없음)이 입력 경로에 그대로
  나타나는 지점이다 — 통째로 들어가지 않는 rung은 애초에 그려지지 않으므로, 그 높이의
  클릭은 보이지 않는 것을 접게 된다. `None`이 정직한 답이다.

### D42: 접힘 상태는 `MonitorModel` **안에** 산다 — 스크롤 오프셋과 정반대로
- **Status**: resolved
- **Rationale**: C4/D26은 스크롤 오프셋을 모델 **밖에** 두라고 요구한다 — 휠 한 노치가 문서
  전체를 다시 셰이핑하면 안 되기 때문이다. 접기는 **어떤 rung이 존재하는지**를 바꾸므로
  1단을 무효화해야 **맞다**. 두 상태를 같은 곳에 두면 둘 중 하나는 반드시 틀린다: 접힘을
  밖에 두면 접어도 화면이 안 바뀌고, 오프셋을 안에 두면 idle CPU 부채가 돌아온다.
- 값 자체는 **앱**이 소유한다(`AiMonitorOverlay::folds`). 모델은 초당 몇 번씩 텔레메트리에서
  새로 만들어지므로, 사용자가 정한 것은 모델 밖에 살다가 매번 다시 찍혀야 한다 — 앵커가
  이미 쓰는 방식과 같다.

## Known Gaps

- **빈도 미상.** `+N more` 때문에 답답했던 상황이 하루/세션당 몇 번인지 사용자가 명시적으로
  "모르겠다"고 답했다(인터뷰에서 세 차례 질문). 성능 예산이나 우선순위를 이 축으로 정할 수 없다.
- **구체적 실패 장면 부재.** `+N more`를 보고 포기했던 실제 순간이 끝내 제시되지 않았다.
  D6(RECENT CALLS)이 그 대용물이며, 이것이 유일한 수용 기준이다.
- **회귀 신호(anti-success) 미정의.** 일주일 후 "실수였다"고 느끼게 할 행동이 미답변.
  Inversion이 후보 셋을 도출했고 그중 **배지 방치**만 D29/D30으로 막았다. 나머지 둘 —

  부분 복구) — 은 **의도적으로 완화만 하고 측정하지 않는다**. 사용 후 재평가 대상.
- **뷰포트보다 높은 rung은 도달 불가 (구현 중 발견, T5).** C1이 시저 렉트를 금지하므로
  컬링은 항목 통째로만 가능한데, 카드 rung(51.8px)이 콘텐츠 밴드(280px 패널에서 25.8px)보다

#### R13.6: 제목과 컨트롤만 클릭에 답한다

#### R13.7: 제목 클릭은 그 섹션만 뒤집고, 두 번째 클릭이 되돌린다

- **When**: 한 섹션의 제목을 누른다
- **Then**: 그 섹션만 접힌다. 이웃은 움직이지 않는다. 한 번 더 누르면 펴진다

#### R13.8: 패널이 소유한 픽셀의 클릭은 컨트롤이 없어도 패널 것이다

  그리드에 선택 캐럿이 생긴다). 닫혀 있으면 `Passthrough`

**병렬 쌍 (파일 겹침 없음, 인터페이스 의존 없음):**
- **T2 ∥ T3** — `monitor_layout.rs` vs 신규 `monitor_scroll.rs`
- **T6 ∥ T4·T5** — `monitor_layout.rs` vs `monitor_panel.rs`
- **T7 ∥ T8** — `input.rs`+`terminal_app.rs` vs `overlay.rs`

**직렬화의 이유가 파일 겹침뿐인 곳(거짓 의존 아님):** T9 → T10 (`overlay.rs`),
T4 → T5 (`monitor_panel.rs`), T2 → T6 (`monitor_layout.rs`).

## External Dependencies

### Pre-work
- **배지 문구와 손실 문구의 정확한 문자열 확정.** 패널의 기존 문구는 전부 영문이다
  ("Last update …", "(no tasks)", "+N more"). 배지(카운트 + `Cmd+Opt+1` 힌트 + 짧은
  폴백)와 손실 마크(`32 of 400` 형태)의 최종 문자열이 정해져야 T6·T9의 폭 폴백 테스트를
  쓸 수 있다.
- **`Cmd+Opt+1`~`6`이 사용자의 실제 환경에서 다른 것에 잡히지 않는지 확인.**
  D35가 물리 키 매칭을 도입하므로, macOS 시스템 단축키나 사용자 설정과의 충돌 여부는
  코드가 아니라 환경의 사실이다.

### Post-work
- **`docs/architecture.md` 갱신** — G1의 idle-CPU 항목에 2단 셰이핑 계약(C3)을 기록하고,
  G4의 `Grid::resize` 리플로 의존 서술은 그대로 두되 패널이 이제 스크롤 뷰포트를
  갖는다는 사실을 반영.
- **`docs/domain.md`의 ai-monitor 항목 갱신** — "우측 도킹 패널"에 스크롤·sticky 제목·
  섹션 점프를 추가.
- **번복 두 건을 기록** — `overlay.rs`의 "패널은 토글 외 어떤 키도 안 잡는다"와
  `monitor_layout.rs`의 "푸터에 키캡을 그리지 않는다"(R1.4)가 이 기능으로 뒤집혔다는
  사실이 코드 주석에 남아야 다음 사람이 되돌리지 않는다.
