# Spec: vertical-tab-sidebar

## Meta
- **Created**: 2026-07-19
- **Type**: dev
- **Status**: drafting
- **Set**: left-tab-sidebar (`specs/left-tab-sidebar/partition-manifest.md`)
- **Batch**: generated by decompose via specify `mode: batch`
- **Complexity**: Simple (brownfield; single-file layer rework + 4 pure geometry helpers; no shader change; the one genuinely new behavior — fixed-slot overflow — is documented in Known Gaps)

## Goal
Rework the tab-bar `DrawLayer` (`crates/renderer/src/tab_bar.rs`) from a horizontal strip in the top inset into a **vertical left sidebar**: tabs stacked top→bottom in the reserved left band (`ctx.left_inset`), the active tab highlighted, titles truncated to the sidebar width. Expose the sidebar geometry as pure, unit-tested free functions so the app's click hit-test can consume the *same* math (SD2).

## Non-goals
- Adding the `left_inset` primitive to the renderer (owned by `renderer-left-inset`; this feature only *reads* `ctx.left_inset`).
- Wiring `set_left_inset`, registering the layer, handling mouse clicks (owned by `tab-click-switch`).
- Changing the `TabBarModel` shape or the one-way data flow (SD3).
- Visual polish beyond a first-cut dark styling (icons, close buttons, drag-reorder, tooltips).

## Confirmed Goal
`TabBar::record` reinterprets the reserved band as a full-window-height sidebar whose width is `ctx.left_inset`. `rects()` paints a left-edge strip background, a highlight over the active tab's vertical slot, and a right-edge vertical border. `text()` lays out each title horizontally (left-aligned, vertically centered) inside its top→bottom slot, truncated to the sidebar width. New pure free functions — `width_px(cell_w)` (the sidebar width the app feeds to `set_left_inset`), `tab_height_px(cell_h)` (per-tab slot height), and `tab_at(x, y, sidebar_w, tab_h, count) -> Option<usize>` (the cursor→tab-index hit-test) — are the single source of truth for both drawing and click routing.

## Declared Surface
- feature-id: vertical-tab-sidebar
- depends_on: [renderer-left-inset]
- declared-surface:
  - crates/renderer/src/tab_bar.rs

## Research
- Today the layer draws a **horizontal** strip: `record()` reads `h = ctx.top_inset`, guards `h <= 0.0`, and lays tabs left→right with `tabw = vw / n` (`crates/renderer/src/tab_bar.rs:312-375, 383-393`).
- `rects()` builds: full-width strip `[0,0,vw,h]`, active highlight `[active*tabw, 0, tabw, h]`, bottom border `[0, h-BORDER_H, vw, BORDER_H]` (`tab_bar.rs:312-331`). These become: left strip `[0,0,w,vh]`, active highlight `[0, slot_y(active,tab_h), w, tab_h]`, right border `[w-BORDER_W, 0, BORDER_W, vh]`. Note `BORDER` (`0x0A0D11`) is the border *color*; the thickness is `BORDER_H = 1.0` (`tab_bar.rs:53,60`), renamed to a neutral `BORDER_W` for the vertical edge so the rect never subtracts a color.
- `text()` centers vertically via `text_top = (h-ch)*0.5`, advances the pen horizontally per glyph, truncates to `max_chars = floor((tabw - 2*PAD_X)/cw)` (`tab_bar.rs:335-375`). For the sidebar, `max_chars` is derived from `w` (sidebar width) and the pen still advances horizontally within each slot; vertical centering is per-slot.
- `height_px(cell_h) = (cell_h*1.5).round().max(1.0)` is the current "band size" helper the app mirrors so inset and layer agree (`tab_bar.rs:66-69`). Its twins for the sidebar are `width_px(cell_w)` (band width) and `tab_height_px(cell_h)` (per-tab slot).
- The layer's own inline `RECT_WGSL`/`TEXT_WGSL` shaders map arbitrary top-left-origin px rects → clip using only `viewport` (`tab_bar.rs:111-165`); drawing vertical rects needs **no shader change**, only different rect coordinates.
- `TabBarModel { titles: Vec<String>, active: usize }` + `TabModelHandle` (`Rc<RefCell<_>>`) is the one-way data flow the app writes and the layer reads (`tab_bar.rs:23-47`); its shape is unchanged (SD3), so the app's model construction is untouched.
- `TAB_BAR_Z = 10` and the `DrawLayer` impl / `add_layer` registration seam are unchanged (`tab_bar.rs:63, 378-450`).
- Existing tests assert the horizontal geometry (`rects_include_strip_highlight_and_border`, `no_highlight_when_active_out_of_range`, `height_scales_with_cell`, `truncate_is_char_safe`) — these are rewritten for the vertical layout since this feature owns the whole file (`tab_bar.rs:541-597`).
- Rules: renderer stays window/app-agnostic (dependency direction); no GUI crates; no `unwrap()` outside tests.

## Decisions

<!-- Inherited verbatim from the set's partition manifest (## Shared Decisions). -->

### SD1: The reserved tab band moves from a top inset (reserves rows) to a left inset (reserves columns)
- **Status**: resolved
- **Rationale**: The sidebar is vertical on the left, so the grid must shrink in *width*, not height. A `left_inset` (physical px reserved left of the grid) mirrors the existing `top_inset` seam exactly: `grid_dims` subtracts it from usable width so `cols` shrink while `rows` stay full; the bg/glyph shaders shift `px.x` right by `left_inset` just as they shift `px.y` by `top_inset`; `FrameCtx` carries it so the tab layer reads one authoritative value. `top_inset` is kept in the renderer (additive, unremoved) but driven to `0.0` by the app once the sidebar is on the left. Rejected: repurposing/renaming `top_inset` (breaks the additive-seam precedent and the cursor/image layers that already read `top_inset`); a separate width-only code path (duplicates the proven inset arithmetic).

### SD2: Tab-strip geometry is defined ONCE in `tab_bar.rs` as pure functions; the app's click hit-test consumes the SAME functions
- **Status**: resolved
- **Rationale**: Click-to-switch must map a cursor (x, y) to a tab index using the exact geometry the layer draws with. Duplicating the layout math in the app would drift. So `tab_bar.rs` owns the geometry as pure, unit-testable free functions (extending the existing `height_px(cell_h)` precedent), named authoritatively so the consumer imports the right symbols: `width_px(cell_w) -> f32` (the sidebar width the app feeds to `set_left_inset`), `tab_height_px(cell_h) -> f32` (the per-tab slot height / stride), a shared forward `slot_y(index, tab_h) -> f32` the draw path uses to place each slot's top, and its exact inverse `tab_at(x, y, sidebar_w, tab_h, count) -> Option<usize>` the click path uses. Because slots have no top pad or inter-slot gap, `slot_y` (`index*tab_h`) and `tab_at` (`floor(y/tab_h)`) are exact inverses; a round-trip unit test pins their agreement so drawing and hit-testing cannot silently diverge. The app calls `set_left_inset(width_px(cell_w))` and, on a left-button press inside the sidebar, routes through the hit-test → `Tabs::jump(i)`; the SAME `set_left_inset(width_px(..))` wiring runs on the config-reload path so the reserved band never goes stale against the drawn sidebar. Rejected: computing tab bounds independently in the app (two sources of truth, guaranteed drift); exposing only raw slot rectangles (pushes the floor/bounds logic back into the caller, re-opening the drift this closes).

### SD3: Preserve the existing tab architecture and chords; click-to-switch is purely additive
- **Status**: resolved
- **Rationale**: The tab set (`Tabs`), the `TabAction` chord table (Cmd+T/W, Cmd+Shift+[/], Cmd+1..9), the one-way `TabModelHandle` data flow (app writes `TabBarModel`; renderer only reads), the `DrawLayer` registration seam (`add_layer`, z-order), and the enforced dependency direction `common ← term-core ← renderer ← app` all stay intact. The renderer never reaches into `crates/app`; the app never hands the renderer a live `Grid`. Click routing is a new `WindowEvent::MouseInput`/`CursorMoved` handler in the app that reuses the existing `Tabs::jump` + `sync_tab_model` + `redraw` path — no new switching logic. Rejected: adding a widget/GUI crate for hit-testing (violates the `no-gui-crates` rule — draw and hit-test on the cell grid ourselves).

### SD4: Every feature lands green under the project's fixed gates, including the insta suite
- **Status**: resolved
- **Rationale**: Each feature must leave `cargo build`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace` (which includes the `term-core` insta snapshot tests) passing, with no `unwrap()` outside tests and per-crate `thiserror` error enums. The vte→grid insta snapshots construct grids at fixed sizes and are not expected to change; if any snapshot output shifts, it is reviewed and accepted via `/insta-review` rather than blindly overwritten. Renderer inset arithmetic stays a unit-testable free function (no GPU needed), matching the `grid_dims`/`height_px` test precedent. Rejected: skipping clippy/tests between features (each spec is independently verifiable and build-order-ready).

### D5: The reserved band is read as a full-height sidebar of width `ctx.left_inset`
- **Status**: resolved
- **Rationale**: `record()` reads `w = ctx.left_inset` (the value `renderer-left-inset` now carries on `FrameCtx`) and guards `w <= 0.0` (twin of today's `h <= 0.0` guard). The strip spans `[0, 0, w, viewport_height]`. This depends on `renderer-left-inset` having added `FrameCtx::left_inset`; referencing `ctx.left_inset` before that field exists would not compile — hence the `depends_on` edge. Rejected: keeping `ctx.top_inset` as a proxy (the grid would reserve rows, not columns — wrong axis).

### D6: Fixed-height tab slots stacked top→bottom; active slot highlighted; right-edge vertical border
- **Status**: resolved
- **Rationale**: Each tab occupies a fixed-height slot of height `tab_h = tab_height_px(cell_h)` from the top, in order, with the slot top given by the shared forward helper `slot_y(i, tab_h) = i*tab_h` (D7). `rects()` returns: strip `[0, 0, w, vh]`; active highlight `[0, slot_y(active, tab_h), w, tab_h]` (only when `active < titles.len()`); right-edge vertical border `[w - BORDER_W, 0, BORDER_W, vh]` separating the sidebar from the grid. **Note on constants:** the existing `BORDER` symbol is the border *color* (`0x0A0D11`); the thickness is a separate scalar — reuse the existing `BORDER_H = 1.0` renamed to a neutral `BORDER_W` (thickness in px) so the rect uses `w - BORDER_W`, never subtracting a color. Fixed slots (vs. dividing the height by tab count) make the per-tab extent — and therefore the hit-test — independent of how many tabs are open, keep titles a readable constant height, and mirror how real vertical tab UIs (activity bars) behave. Rejected: even height division `vh/n` (slot size and hit-target shrink as tabs multiply; the click math would depend on `n`); overflow scrolling (deferred — tab counts are small for a daily driver, a documented first-cut limit).

### D7: Expose `width_px`, `tab_height_px`, `slot_y`, and `tab_at` as pure free functions — the single geometry source (SD2)
- **Status**: resolved
- **Rationale**: Pure free functions, twins of the existing `height_px`, are the one place sidebar geometry lives, with **concrete formulas pinned** (they cannot be left to the implementer — an under-sized width silently truncates every title to zero chars via D8):
  - `pub fn width_px(cell_w: f32) -> f32 = (cell_w * 14.0).round().max(1.0)` — ~14 columns wide, so D8's `max_chars = floor((w - 2*PAD_X)/cw)` yields ≈12 visible chars for a typical cell (never 0).
  - `pub fn tab_height_px(cell_h: f32) -> f32 = (cell_h * 1.5).round().max(1.0)` — the height twin of `height_px` (=30 for a 20px cell, matching R2.1).
  - `pub fn slot_y(index: usize, tab_h: f32) -> f32 = index as f32 * tab_h` — the shared **forward** placement the draw path (highlight + title y) uses.
  - `pub fn tab_at(x: f32, y: f32, sidebar_w: f32, tab_h: f32, count: usize) -> Option<usize>` — the **inverse**: `Some(i)` iff `0.0 <= x < sidebar_w` **and** `0.0 <= y` **and** `i = floor(y / tab_h) < count`, else `None`.
- **Steelman addressed:** exposing a hit-test does not by itself unify drawing (forward, `index→y`) and clicking (inverse, `y→index`) — those remain two directions of the same map. What makes them a single source is that BOTH derive from `slot_y`/`tab_height_px` with **no top pad and no inter-slot gap**, so `tab_at` is the exact arithmetic inverse of `slot_y`. A round-trip unit test (for every `i`, a click at the vertical center of `slot_y(i, tab_h)` returns `Some(i)`) pins that inverse relationship, so adding a pad later fails the test rather than silently drifting. `record()`/`rects()`/`text()` place slots via `slot_y`; the app (`tab-click-switch`) imports `tab_at`. Rejected: exposing raw slot rectangles instead of a hit-test (pushes the floor/bounds logic into the caller, re-opening the drift SD2 closes); leaving `width_px` as prose (the one scalar that, wrong, makes the whole sidebar useless).

### D8: Titles render horizontally, left-aligned + vertically centered in each slot, truncated to the sidebar width
- **Status**: resolved
- **Rationale**: Within each top→bottom slot the title is drawn left-to-right with the existing monospace advance, indented by `PAD_X`, vertically centered on the slot (`text_top = slot_y + (tab_h - ch)*0.5`, baseline `+ ascent`), and truncated with the char-safe `truncate` to `max_chars = floor((w - 2*PAD_X)/cw).max(0)` so a title never spills past the sidebar or into the grid. Keeping horizontal text (rather than rotating glyphs vertically) reuses the atlas path unchanged and stays readable. Rejected: rotated/vertical text (needs glyph rotation the atlas path doesn't support; poor readability).

### D9: `TabBarModel` shape is unchanged — one-way data flow preserved (SD3)
- **Status**: resolved
- **Rationale**: The sidebar needs exactly what the strip needed — `titles` + `active` — so `TabBarModel { titles: Vec<String>, active: usize }` and `TabModelHandle` are kept as-is. The app writes the model exactly as before; only the layer's *interpretation* (vertical vs horizontal) changes. This keeps `tab-click-switch` from having to touch the model type. Rejected: adding per-tab geometry to the model (the layer derives geometry from `cell`/`left_inset`; the model stays pure content).

## Constraints
- `crates/renderer/src/tab_bar.rs` must not import `winit` or any `crates/app` type; data flows in only via `TabModelHandle` (dependency direction; SD3).
- The layer must read the band width from `ctx.left_inset` (not a hardcoded constant), so it stays in lockstep with whatever the app set (SD1/SD2).
- `width_px`, `tab_height_px`, `tab_at` must be pure (no GPU/state) and unit-tested without a device.
- No GUI/widget crate; draw with the existing inline rect/text pipelines.
- No `unwrap()` outside `#[cfg(test)]`.
- `cargo build`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` all green (SD4).

## Known Gaps
- Overflow when the stacked tabs exceed the window height (tabs below the last visible slot are clipped) — a documented first-cut limit; scrolling/condensing is deferred. Worst corner: if the *active* tab overflows, its highlight is drawn off-screen and it is click-unreachable — reachable only via a keyboard chord until overflow handling lands.
- cwd-basename titles still come from the app's `Tabs::titles()`; this feature does not change the title source.

## Requirements

### R0: The tab bar draws as a vertical left sidebar and exposes reusable geometry
Seeded from the manifest `accept-seed`.

#### R0.1: Tabs render stacked top→bottom in the left band with the active tab highlighted
- **Given**: A `TabBarModel` with 3 titles, `active = 1`, drawn with `left_inset = 160.0` and window height `800.0`
- **When**: `record()` builds its rects for the frame
- **Then**: A full-height strip `[0,0,160,800]` is drawn, the active highlight sits over slot 1 at `[0, slot_y(1,tab_h), 160, tab_h]`, and a right-edge border at `[160-BORDER_W, 0, BORDER_W, 800]` (`BORDER_W` = thickness, not the `BORDER` color)

### R1: `record()` reads the sidebar width from `ctx.left_inset`
Derives from D5.

#### R1.1: Zero left inset draws nothing
- **Given**: A frame where `ctx.left_inset == 0.0`
- **When**: `record()` runs
- **Then**: It returns early and issues no draw (twin of the old `top_inset <= 0` guard)

#### R1.2: The strip spans the full window height at the inset width
- **Given**: A frame with `ctx.left_inset == 160.0` and viewport height `540.0`
- **When**: `rects()` builds the strip background
- **Then**: The strip rect is `[0.0, 0.0, 160.0, 540.0]`

### R2: Vertical slot layout — highlight + border geometry
Derives from D6.

#### R2.1: The active highlight covers the active tab's vertical slot
- **Given**: A model with `active = 2`, `tab_h = 30.0`, sidebar width `w`
- **When**: `rects()` builds the highlight
- **Then**: The highlight rect is `[0.0, 60.0, w, 30.0]` (y = `active * tab_h`)

#### R2.2: No highlight when the active index is out of range
- **Given**: A model with one title but `active = 5` (stale)
- **When**: `rects()` runs
- **Then**: Only the strip + right border are produced (no highlight rect)

#### R2.3: A right-edge vertical border separates the sidebar from the grid
- **Given**: Sidebar width `w = 160.0`, viewport height `vh = 540.0`, thickness `BORDER_W`
- **When**: `rects()` builds the border
- **Then**: The border rect is `[160.0 - BORDER_W, 0.0, BORDER_W, 540.0]` (a vertical line on the right edge; `BORDER_W` is the thickness scalar, not the `BORDER` color)

### R3: Pure geometry functions are the single source of truth (SD2)
Derives from D7.

#### R3.1: `width_px` and `tab_height_px` scale with cell size and leave room for titles
- **Given**: Cell width/height values `10.0` and `20.0`
- **When**: `width_px(20.0)` / `width_px(10.0)` and `tab_height_px(20.0)` / `tab_height_px(10.0)` are compared, and `max_chars = floor((width_px(cw) - 2*PAD_X)/cw)` is computed
- **Then**: The larger cell yields the larger result, every result is `>= 1.0`, AND `max_chars >= 8` for a typical `cw` (e.g. `cw = 8.0`) — i.e. `width_px` is wide enough that D8's truncation never collapses to 0 chars

#### R3.2: `tab_at` maps a cursor inside a slot to that tab index
- **Given**: `sidebar_w = 160.0`, `tab_h = 30.0`, `count = 3`
- **When**: `tab_at(40.0, 65.0, 160.0, 30.0, 3)` is called (x inside the band, y in slot 2)
- **Then**: It returns `Some(2)` (`floor(65/30) = 2 < 3`)

#### R3.3: `tab_at` rejects clicks outside the band, above the strip, or below the last tab
- **Given**: `sidebar_w = 160.0`, `tab_h = 30.0`, `count = 3`
- **When**: `tab_at(200.0, 65.0, ..)` (x past the sidebar), `tab_at(40.0, 500.0, ..)` (y below slot 2), and `tab_at(40.0, -5.0, ..)` (y above the strip) are called
- **Then**: All three return `None` (the `0.0 <= y` guard prevents a negative `y` from casting to slot 0)

#### R3.4: `slot_y` and `tab_at` are exact inverses (drawing ↔ hit-test agreement)
- **Given**: `sidebar_w = 160.0`, `tab_h = 30.0`, `count = 3`
- **When**: For each `i` in `0..3`, a click at the vertical center of its drawn slot — `tab_at(80.0, slot_y(i, 30.0) + 15.0, 160.0, 30.0, 3)` — is evaluated
- **Then**: It returns `Some(i)` for every `i` (the forward `slot_y` the layer draws with and the inverse `tab_at` the app clicks with never disagree)

### R4: Titles are laid out per-slot and truncated to the sidebar width
Derives from D8.

#### R4.1: A title is truncated to the chars that fit the sidebar width
- **Given**: Sidebar width `w`, `PAD_X`, cell width `cw`, and a title longer than `floor((w - 2*PAD_X)/cw)` chars
- **When**: `text()` lays the title out
- **Then**: Only the first `floor((w - 2*PAD_X)/cw)` chars are emitted as glyph quads (char-safe, never splitting a codepoint), all within the sidebar band

#### R4.2: Each title is vertically centered within its own slot
- **Given**: Tabs at slots `0..n` with slot height `tab_h` and cell height `ch`
- **When**: `text()` places tab `i`'s baseline
- **Then**: Its text top is `slot_y(i, tab_h) + (tab_h - ch)*0.5` (centered in that slot via the shared forward helper, not the whole strip)
